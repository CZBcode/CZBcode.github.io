第5章 · 工程部署和性能优化 — 性能优化方案

发布于 2026-06-01 | 分类：技术笔记 | Agent开发学习路线

缓存优化（Embedding向量缓存/上下文缓存/批量向量化）、推理加速（vLLM PagedAttention/SGLang/动态批处理）、上下文智能裁剪。

Agent服务的性能瓶颈在哪里？

一个典型的Agent请求链路中，耗时分布大致如下：

  1. LLM推理：60~80%（最大的瓶颈）
  2. Embedding向量化：10~15%
  3. 向量检索：3~5%
  4. 工具调用：5~15%
  5. 其他：2~5%

优化要抓住大头——LLM推理和Embedding。

6.1 缓存优化

6.1.1 Embedding向量缓存

相同文本的embedding结果是固定的，没必要重复计算：

  • 用文本hash作为key，向量作为value
  • Redis/MemoryCache做缓存层
  • 命中率通常可达60~80%
  • 节省大量API调用费用和延迟

6.1.2 常用上下文缓存

系统Prompt、用户画像、工具描述等内容在每个请求中都重复出现：

  • 将这些固定内容提前计算KV Cache
  • 支持Prefix Caching的推理框架：vLLM、SGLang
  • 对于长System Prompt效果尤其明显

6.1.3 批量向量化处理

  • 单个文本调用Embedding API效率低
  • 积累一批文本后批量调用（batch_size=32~256）
  • 吞吐量可提升5~10倍

6.2 推理加速

6.2.1 vLLM + PagedAttention

vLLM是目前最受欢迎的高性能推理引擎：

  • PagedAttention：类似操作系统的虚拟内存管理，解决KV Cache碎片化问题
  • Continuous Batching：请求级别的连续批处理，不用等最慢的请求
  • Tensor Parallelism：多GPU并行推理
  • 效果：吞吐量比HuggingFace Transformers提升2~4倍

6.2.2 SGLang

专为Agent场景优化的推理引擎：

  • 结构化输出：原生支持Constrained Decoding（强制输出符合JSON Schema）
  • RadixAttention：前缀树共享，相同前缀的请求共享KV Cache
  • 无限并发：高效的请求调度

6.2.3 动态批处理（Dynamic Batching）

  • 不要一个个处理请求！
  • 积累一小批请求（窗口期10~50ms）
  • 打包成一个batch一起推理
  • GPU利用率从20%提升到80%+

6.3 上下文优化

减少送入模型的Token数量，直接降低延迟和成本。

6.3.1 智能裁剪

  • 保留关键对话（用户指令、重要结论）
  • 删除冗余内容（寒暄、重复确认、错误尝试）
  • 用重要性评分模型自动评估每句话的价值

6.3.2 摘要替代

  • 早期对话用一句话摘要代替原始内容
  • 保留最近的完整对话（如最近5轮）
  • 摘要 + 近期详情的组合策略

6.3.3 分层记忆减负

  • 不在上下文中放所有历史
  • 只放当前任务相关的记忆（通过RAG召回）
  • 长期记忆按需检索，不常驻上下文

性能优化的ROI排序

  1. 缓存（投入最小，收益最大）→ Embedding缓存 + 上下文缓存
  2. 批处理 → 动态批处理 + 批量向量化
  3. 推理引擎 → vLLM / SGLang 替换原生推理
  4. 上下文优化 → 摘要压缩 + 智能裁剪
  5. 模型量化 → INT4/INT8 量化（最后考虑，有精度损失）
