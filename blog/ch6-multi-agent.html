第6章 · 多Agent高阶系统

发布于 2026-06-01 | 分类：技术笔记 | Agent开发学习路线

多Agent角色体系（决策者/检索执行/代码开发/审核校验/调度管理）、中心化调度vs去中心化协商、通信协议与权限隔离。

从单Agent到多Agent

当任务复杂度超过单个Agent的能力边界时，就需要多Agent协作。就像现实世界一样——一个人搞不定的事，就组个团队来做。

7.1 多Agent分工体系

7.1.1 决策者Agent（The Orchestrator）

  • 职责：理解用户意图，拆解任务，分配给合适的Agent
  • 能力：全局视野、任务规划、质量控制
  • 类比：项目经理 / 产品经理

7.1.2 检索执行Agent（The Retriever）

  • 职责：从知识库、搜索引擎、数据库中检索信息
  • 能力：RAG、搜索、数据查询
  • 类比：研究员 / 图书管理员

7.1.3 代码开发Agent（The Coder）

  • 职责：编写、修改、调试代码
  • 能力：代码生成、Code Review、Bug修复
  • 类比：软件工程师

7.1.4 审核校验Agent（The Reviewer）

  • 职责：检查其他Agent的输出质量
  • 能力：事实核查、安全审计、格式校验
  • 类比：QA工程师 / 审计师

7.1.5 调度管理Agent（The Coordinator）

  • 职责：管理Agent之间的消息传递、状态同步、异常处理
  • 能力：任务分发、进度跟踪、冲突解决
  • 类比：Scrum Master / 团队协调人

7.2 协作模式

7.2.1 中心化统一调度

有一个主控Agent负责全局调度：

用户请求
    ↓
[主控Agent] ←── 分析任务，制定计划
    ├──→ [检索Agent] → 返回参考资料
    ├──→ [代码Agent] → 编写解决方案
    └──→ [审核Agent] → 检查质量
    ↓
[主控Agent] ←── 汇总结果，生成最终回答
    ↓
返回给用户
  • 优点：流程清晰、易于调试、适合流程明确的任务
  • 缺点：主控Agent成为瓶颈、灵活性有限

7.2.2 去中心化自主协商

各Agent平等交流，自主决定行为：

  • Agent之间通过消息总线通信
  • 每个Agent自主决定是否参与、贡献什么
  • 通过多轮协商达成共识
  • 优点：灵活、鲁棒、适合开放式问题
  • 缺点：难以预测、调试困难、可能陷入死循环

7.3 通信与协议

7.3.1 统一消息格式

{
  "message_id": "msg_001",
  "sender": "orchestrator",
  "receiver": "retriever",
  "message_type": "task_request",
  "payload": {
    "query": "查找2024年Q4的销售数据",
    "sources": ["database", "api"],
    "deadline": "30s"
  },
  "timestamp": "2026-06-01T16:00:00Z"
}

7.3.2 权限隔离

  • 每个Agent只能访问被授权的工具和数据
  • 代码Agent不能直接操作生产数据库
  • 检索Agent不能执行任意代码
  • 最小权限原则，防止误操作和安全风险

7.3.3 任务分片

  • 大任务拆分为小的、独立的子任务
  • 子任务可以并行执行
  • 每个子任务有明确的输入输出规范
  • 支持部分失败（某个子任务失败不影响整体）

7.3.4 状态同步

  • 共享的状态存储（如Redis）记录全局进度
  • 每个Agent更新自己的状态
  • 其他Agent可以订阅状态变更
  • 异常状态触发告警和干预

7.3.5 异常同步

  • 某个Agent失败时立即通知相关Agent
  • 触发重试或降级策略
  • 必要时升级为人工处理
